# Security Notes

Film handles sensitive production data, including contracts, releases, private contacts, SMS consent, and financial summaries. Security work is part of the MVP, not a later cleanup pass.

## Current Boundaries

- Provider integrations default to dry-run. Resend is live only for member-eligible magic links and explicitly gated workspace invites; Stripe reads are live only through the summary-only Pool/Store adapters.
- Remote Cloudflare D1/KV/R2 MVP resources and the `film-worker` script exist, with `RESEND_API_KEY`, `INVITE_DELIVERY_WEBHOOK_SECRET`, `STRIPE_WEBHOOK_SECRET`, and `STRIPE_SUMMARY_ADAPTER_SECRET` stored as Cloudflare secret names only. The Worker route targets `https://api.film.dustwave.xyz`, the app origin is `https://film.dustwave.xyz`, and live invite delivery is explicitly gated through `INVITE_DELIVERY_MODE=live`.
- Invite delivery suppressions are enforced by target hash before invite creation. When a bounced, complained, or provider-suppressed target hash exists in D1, `POST /api/invites/create-dry-run` returns `invite_delivery_suppressed`, records bounded audit metadata, and does not create an invite row, delivery attempt, or Resend request.
- `workers_dev` is disabled so the API Worker is exposed only through its configured custom domain.
- `npm run check:deploy` reports production route/origin, invite delivery, and Stripe summary-readiness blockers by configuration name without printing secret values; it validates exact http(s) origins, production HTTPS `/film/stripe-summary` adapter URLs, and usable Pool/Store mapping refs. Operators can add `-- --wrangler-secrets` to count Cloudflare secret names without reading values. `npm run check:deploy:strict` is the production readiness gate.
- Credentialed Worker CORS responses only echo configured allowed origins. Unknown browser origins receive a non-matching allow-origin value so browsers block credentialed access.
- Workspace member seed data uses email hashes, not raw email addresses.
- D1 migrations include workspace invite, invite delivery outbox, verified invite-delivery webhook metadata, hash-only invite delivery suppressions, project membership-scope, and record permission tables. Invite creation stores invite targets and tokens as hashes only, revokes older pending invites for the same workspace/email hash, records a Resend delivery attempt with the target hash only, and returns the development-only token only for dry-run delivery. Live invite delivery requires `INVITE_DELIVERY_MODE=live`, Resend API key, sender, production app origin in `ALLOWED_ORIGINS`, and webhook secret; the Worker inserts a `queued_live` delivery row before calling Resend, then updates that row to `sent_live` or `failed_live_delivery` with provider message ID or bounded error code. Raw invite email and invite token are sent only to Resend in the live API request and are not stored in D1, audit events, backups, local mirrors, or operation logs. The Resend invite-delivery webhook route requires Svix ID, timestamp, and signature headers, verifies them with `INVITE_DELIVERY_WEBHOOK_SECRET`, rejects stale signatures, deduplicates by Svix message ID, links known live delivery attempts by provider message ID, stores only delivery status, IDs, timestamps, and metadata-key names, and updates the linked attempt's latest event status. Bounced, complained, and suppressed events create or refresh `invite_delivery_suppressions` rows keyed by provider, target hash, and reason. It does not persist raw webhook payloads, raw recipient addresses, headers, or secret values. Protected invite manifest, delivery suppression manifest, and revoke routes expose pending invite IDs, email hashes, roles, expiry metadata, target hashes, suppression reasons, linked attempt/message IDs, and timestamps only to owner/producer sessions; revocation requires an exact workspace, invite ID, email hash, and role match before marking a pending invite revoked. A protected invite-delivery readiness route reports missing Resend/live-delivery configuration and compliance blockers without exposing secret values. Invite acceptance resolves the token hash in the Worker, creates or updates a workspace member, activates the member status, and marks the invite accepted before magic-link sign-in can create a session.
- Browser backups export as ZIP containers with a plaintext non-secret manifest plus encrypted workspace, document-body, and attachment restore-policy payloads, use PBKDF2 plus AES-GCM, recursively exclude provider-token-shaped fields by schema policy, and include attachment metadata without blob bytes. The manifest records document-body and attachment-policy payload counts only, not document names, document body text, attachment paths, object keys, or attachment hashes. Legacy JSON backup previews remain readable.
- Backup dry-runs record restore-point metadata in D1 when available and prune to the latest five per workspace. The dry-run route remains a metadata-only fallback when R2 storage is unavailable.
- The web backup UI still downloads encrypted ZIP backups locally first. It can then send those already-encrypted ZIP bytes to the Worker R2 backup upload route. That route requires owner/producer CSRF/session authorization when D1 auth storage is available, workspace scope checks, the exact `STORE BACKUP <workspaceId>` confirmation header, a valid backup timestamp, a bounded declared size, a matching SHA-256 over the received bytes, and the `BACKUPS` R2 binding before writing the object and recording restore-point metadata. Backup passphrases and decrypted workspace payloads are never sent to the Worker.
- Encrypted backup object upload requires both D1 and R2, reads bytes through the declared-size/capped stream helper, and uses a deterministic create-only R2 key plus deterministic restore-point identity. Exact existing objects are recoverable retries only when size and all ownership/hash/format metadata match. Restore-point insertion, latest-five retention, and audit evidence are one D1 batch. Until that batch succeeds the endpoint returns 503 `r2_backup_metadata_pending`; it never reports an unlisted R2 object as a completed backup.
- Stored backup export is Worker-owned. The manifest route requires owner/producer CSRF/session authorization, workspace scope checks, and a bounded row limit. Before bytes can be downloaded, the browser must request `POST /api/backups/r2/object-download-plan`; the Worker resolves the D1 restore-point ID to an R2 key, checks the `BACKUPS` object exists, stores a 15-minute hashed download token in `backup_object_download_plans`, and records bounded audit metadata with `destructiveWrite: false`. The object route accepts a D1 restore-point ID plus the matching plan ID/token rather than a browser-supplied object key, rejects missing, expired, mismatched, or invalid plans, confirms that the restore point belongs to the workspace and points at the `film-backups` R2 namespace, validates the derived object key prefix, then reads that exact object from the `BACKUPS` R2 binding.
- Stored backup preview downloads encrypted ZIP bytes through the Worker, then prompts for the passphrase and decrypts in the browser only. It reuses the existing non-destructive restore preview and does not commit records.
- Encrypted backup previews decrypt in the browser only after a passphrase prompt, summarize matching/new project counts, per-record status, and field-level overwrite conflicts, do not store the passphrase, and do not overwrite local records.
- Workspace mutations are recorded in a local operation log before future sync.
- Magic-link auth is Worker-owned. Local Wrangler explicitly uses `AUTH_MAGIC_LINK_MODE=dry_run` for deterministic tests. Production requires `AUTH_MAGIC_LINK_MODE=live`, D1, KV, Resend, and an active member matching the normalized email hash. Requests return the same generic accepted response for known and unknown addresses; only active members receive an email. Tokens are random, short-lived, one-time, stored only as hashes, and bound to the member/workspace. Resend click/open tracking is disabled for the sending domain so authentication and invitation URLs are not rewritten through a tracking redirect. Newly issued magic-link and invite tokens use URL fragments so the static host does not receive them; the browser consumes and removes the fragment before rendering, while legacy query links remain accepted only for already-issued messages. Verification and protected authorization fail closed on D1/KV errors, inactive membership, workspace mismatch, or legacy workspace-less/member-less sessions. The returned CSRF token is retained only in same-tab `sessionStorage`; reload restoration must match the HttpOnly cookie's read-only session ID/expiry metadata before the token is reused, and a new tab requires a new magic link.
- D1-backed auth also checks workspace member status. Invited or disabled members cannot verify magic links into sessions, read session metadata, or use protected mutations. Owner/producer sessions can update active/disabled member status through a protected Worker route; the route rejects workspace mismatches, rejects self-disable, requires owner role for owner targets, and atomically applies the status, disable-time target-session revocation, and bounded audit metadata without raw email addresses. Reactivation does not revive revoked sessions.
- Project membership, record permission, and core owner mutations commit current-state assertions, authorization changes, and bounded audit evidence in one D1 transaction. Membership assignment rejects project IDs owned by another workspace. Permission upserts preserve existing durable grant IDs, while revocation requires the exact current grant timestamp; owner transfer requires the exact prior owner and an active target member.
- Metadata-only comment creation reasserts the target and current owner/comment permission inside the D1 transaction, stores only a bounded preview and SHA-256, and commits audit evidence with the intent. Core and film-profile mutation request creation and approval/rejection likewise commit exact target/request assertions, state, and audit evidence together; storage failures return 503 without orphaned review artifacts.
- Invite acceptance asserts the exact pending token and expected member identity before applying role/status, token consumption, and hash-only audit evidence in one transaction. Exact pending-invite revocation and audit evidence are also atomic; concurrent or stale invite state fails before membership or invite changes.
- Magic-link verification atomically asserts the unconsumed/unexpired link and active member, consumes the one-time link, and inserts the D1 session. D1 is authoritative for member-bound sessions; post-commit KV role-cache failures do not hide a valid session, and post-revocation KV deletion failures cannot revive a logged-out session. Live rate limiting still requires KV and fails closed before verification.
- Live magic-link email uses the random persisted D1 link-record ID as a Resend idempotency key. The key contains no recipient, email hash, raw token, or token-derived value and is not exposed to the browser; provider delivery is not attempted without successful D1 link persistence.
- Current D1 membership is authoritative for a member-bound session's role and workspace. Stale KV role values cannot preserve elevated access after a D1 downgrade, and member/session workspace mismatches are rejected.
- Member-status query failure does not fall back to assumed active membership. Live logout with a session cookie returns 503 and retains the cookie when D1 cannot confirm the revocation path.
- With D1 bound, record comment/mutation authorization and invite/member/membership/permission/owner/mutation-request operations return unavailable errors on D1 exceptions; they never grant access or report memoryless success.
- D1 operation replay failures return 503 with zero accepted IDs, preventing the browser from clearing operations that were not durably applied. Newly accepted canonical creates, relationship rows, and their operation-log evidence execute in one guarded D1 batch; any failure rolls back the sequence rather than leaving earlier operations applied.
- Invite creation returns 503 without calling Resend when suppression or invite storage is unavailable; prior-invite revocation and replacement insertion use a transactional D1 batch.
- Invite acceptance batches member role, active status, and token consumption, and succeeds only when one pending invite is consumed.
- Verified invite webhook event, attempt status, and optional suppression writes are one transactional D1 batch; persistence failure returns 503 so the provider can retry.
- Live invite sends use a Resend idempotency key and a non-PII delivery-attempt tag, allowing signed callbacks to recover and backfill a provider message ID that failed to persist after send.
- Workspace-scoped protected mutations compare request workspace IDs against the authenticated D1 session workspace and fail closed on mismatches.
- Canonical workspace snapshots require CSRF/session authorization and return bounded collections only. Operator roles can read the workspace's core production rows; scoped roles receive project/member/record-permission-filtered rows, sensitive documents require direct ownership or exact permission, sensitive people remain restricted, and expenses remain owner/producer or exact-owner/permission scoped. Snapshots exclude contact fields, private notes, raw audit metadata, provider values, and attachment bytes, and identify any collection truncated by its fixed limit.
- Canonical Markdown body writes are separate from the general mutation allowlist. They accept at most 64 KiB for an existing native/Markdown document, require exact `updated_at` freshness, and batch the body update with hash/length-only audit evidence. Non-operator writes require exact document ownership or an active document `write`/`admin` grant; stale conflicts return without changing D1 and leave the IndexedDB draft intact.
- Project membership, project membership history, owner review/transfer/history, mutation preflight/request/resolution/diff-preview/application/audit-manifest, comment intents, and explicit record permission assignment are Worker-owned, require authorization and CSRF/session checks when D1 auth storage is available, reject workspace mismatches, reject disabled/invited target members, and upsert `project_memberships`, `owner_member_id`, `record_mutation_requests`, `record_comment_intents`, or `record_permissions` rows for the current collaboration guards. Core project/document/task/person/equipment/expense rows carry nullable `owner_member_id` metadata; Worker-applied canonical creates stamp the actor member as owner, owned projects can authorize scoped task/document/equipment creates, and owned documents can authorize metadata-only document update. Owner manifests return only the selected core entity and current owner member ID. Owner transfer validates the target member is active in the workspace, validates the core record belongs to the workspace, updates only a fixed table/id pair, returns the previous owner member ID, and records bounded audit metadata. Owner history validates the core record and returns only transfer-oriented audit metadata for that exact entity: actor member ID, previous owner member ID, new owner member ID, timestamp, count, and truncation status. Mutation preflight validates the selected core row and returns only allowed-by policy metadata without updating or deleting records; non-operator update preflights are limited to project/task/document/equipment row owners or exact unexpired `write`/`admin` grants, while person/expense updates and all delete preflights remain owner/producer-only. Mutation requests reuse the same authorization, validate requested update field keys against the shared `packages/schema` allowlist, store bounded request metadata plus the selected row's expected `updated_at` in `record_mutation_requests`, return `destructiveWrite: false`, and expose request manifests to owner/producer sessions with actor, allowed-by policy, field keys, summary hash/preview, status, expected timestamp, count, and truncation status. The allowlist covers bounded base-table metadata such as project type, document external URL, person sensitivity, equipment notes, and expense comments, but still excludes contact details, payment identifiers, raw document bodies, provider credentials, and cross-table film-profile edits. Owner/producer resolution can approve or reject a request without destructive writes. Approved mutation diff previews validate relationship updates, read only fixed allowlisted core metadata columns, return per-field before/after values plus stale status, and keep `destructiveWrite: false`. Mutation application requires an approved request, `APPLY MUTATION <requestId>` confirmation, fixed table/id routing, allowlisted fields, valid same-workspace project references, active task assignees with project membership, project ownership, or project write/admin permission when the task is project-scoped, a fresh `updated_at` match, and a guarded D1 write that changes one row before updating request status; stale requests or zero-change guarded writes are marked `stale_record_blocked` without treating the request as applied. Applied update requests store field diffs and rollback guidance in bounded application JSON, and owner/producer sessions can scaffold a pending inverse update request from those before values without applying it. Applied delete recovery planning returns backup/recreate blockers and suggested steps rather than storing raw deleted row contents. Request-scoped mutation audit manifests return only the durable request, rollback guidance, and matching audit event metadata keys. Comment intents are limited to project/task/document rows; owner/producer sessions, row owners, or members with exact unexpired `comment`, `write`, or `admin` grants can create them and review their manifests. The Worker stores only a bounded comment preview and SHA-256 hash, not the full body, and the protected manifest returns only preview/hash/author/timestamp metadata for the exact row. The Team inspector can update member active/disabled status, review/remove selected-project team assignments, inspect selected-project team audit history, review/transfer selected project/task/document/person/equipment/expense owners, inspect owner transfer history, preflight selected-row mutation access, create/review selected-row mutation requests through typed field controls, resolve approved/rejected requests, preview approved mutation diffs, apply approved stale-checked mutations, review mutation audit manifests, scaffold applied-update rollback requests, plan applied-delete recovery, create and review metadata-only project/task/document comment intents, and grant, review, revoke, or inspect bounded audit history for selected-project, selected-task, and selected-document permissions through protected Worker routes. Browser people/equipment/expense rows now carry stable IDs so those owner routes target D1-shaped rows rather than natural display names. Project membership removal requires matching project, member, and role fields, and owner project roles require owner authorization. Project membership history validates the selected project and returns only matching membership assign/revoke audit rows with action, actor member ID, target member ID, role, optional department, timestamp, count, and truncation status, not raw audit metadata. Permission manifests expose active/unexpired grants separately from expired grants, and include only member IDs, levels, department scopes, and expiry metadata for owner/producer sessions. Permission history reads only matching permission assign/revoke audit rows and returns action, actor member ID, target member ID, permission level, optional department/expiry, timestamp, count, and truncation status, not raw audit metadata. Permission revocation requires the manifest permission ID plus matching entity, member, and permission fields before deleting a row, and records bounded audit metadata. Project permissions authorize scoped task/document/equipment creates and document-update metadata; exact task/document/equipment permissions can authorize only that entity's canonical create, and exact document permissions can authorize metadata-only document update.
- Film-profile mutations use separate owner/producer Worker routes for runtime, format, shoot-date, and budget metadata because those fields live in `film_profiles`, not the base `projects` row. The preflight route validates workspace/project scope, returns the allowlisted field definitions plus the current `film_profiles.updated_at` stale-check token, and records bounded audit metadata with `destructiveWrite: false`. The Team inspector exposes profile request, manifest, resolution, diff preview, and apply controls from the same field allowlist. Request creation stores bounded metadata in `film_profile_mutation_requests`, resolution is approval-only and non-destructive, and diff previews return before/after metadata plus stale status without writing. Profile apply requires an approved request, `APPLY FILM PROFILE MUTATION <requestId>` confirmation, allowlisted update fields, and a fresh `film_profiles.updated_at` match before inserting a missing profile row or updating the existing row; stale requests are marked `stale_record_blocked` without applying changes.
- Approved core-record and film-profile apply routes now execute the request-status assertion, stale target assertion, target write/delete/insert, request transition with bounded rollback evidence, and deterministic audit event in one D1 batch. Target and request writes must each change exactly one row. Batch failure returns 503 without changing target/request/audit state; stale targets use the separate non-destructive blocked transition.
- POST routes use coarse KV-backed rate-limit buckets keyed by hashed IP/user-agent and route family when `SESSIONS` is available, including invite dry-run routes. Production can tune existing bucket limits/windows through bounded `RATE_LIMIT_OVERRIDES`; malformed or out-of-range overrides are ignored by the Worker and flagged by deployment readiness. Without KV, local development falls back to dry-run behavior.
- The dry-run app shell keeps development magic-link tokens in memory. Verified session metadata plus CSRF are retained only in same-tab `sessionStorage` for reload restoration and are cleared on logout or failed session validation.
- Operation sync requires Worker preflight, CSRF/session authorization, per-operation role authorization, valid kind/entity pairs, timestamps, and bounded payloads before local operations are marked synced. Project onboarding sends only title, controlled type, and template metadata. Task operations send project/title/status/timestamp metadata; authorized D1 replay applies creates and stale-checked status/completion transitions in the same bounded batch as operation-log evidence. `document.updated` operations still carry only project/name/body-length metadata; full Markdown text uses the dedicated body route and never enters `operation_log`. People and expense creates omit contacts, payment details, private notes, and provider data. Cross-workspace relationships, stale task states, unauthorized scopes, duplicate create targets, and failed D1 batches leave operations queued.
- Restore commit dry-run gates are Worker-owned, require owner or producer authorization, require the exact `RESTORE <workspaceId>` confirmation phrase plus bounded preview counts, reject workspace mismatches, verify stored R2 pre-restore backup proof when a restore point ID is provided, and explicitly perform no destructive writes. Without verified proof, the dry-run gate remains blocked at `blocked_until_pre_restore_backup`.
- Restore approval dry-runs use the same authorization, confirmation, workspace, preview, and pre-restore backup proof checks. When D1 is available, they persist `restore_approvals` rows with actor member IDs, preview JSON, proof metadata, `blocked` or `approved_pending_commit` status, and `destructive_write = 0`.
- Restore commit-storage dry-runs require D1 approval storage, a matching `approved_pending_commit` approval row, matching preview/snapshot/backup/proof metadata, and verified pre-restore backup proof before they persist `restore_commit_attempts` with `blocked_until_restore_apply` and `destructive_write = 0`.
- Restore application preflight dry-runs require D1 approval and commit-attempt storage, a matching approved approval row, a matching blocked commit attempt, matching preview/snapshot/backup/proof metadata, and verified pre-restore backup proof before they persist `restore_application_preflights` with rollback guidance, bounded non-authoritative table-plan metadata, `blocked_until_restore_apply_implementation`, and `destructive_write = 0`.
- Restore application commits are Worker-owned for at most 150 workspace snapshot rows: workspace metadata, projects, tasks, documents, people, equipment, and expenses. The visible browser action is available only after a decrypted backup preview and blocked application preflight; it keeps the snapshot in memory and submits bounded snapshot records, not provider secrets or attachment bytes. The endpoint requires owner/producer authorization, CSRF/session checks, exact `RESTORE <workspaceId>` confirmation, matching approved approval row, matching blocked commit attempt, matching blocked application preflight row, verified stored R2 pre-restore backup proof, semantic field and parent-project validation, a workspace-snapshot table plan whose per-table create/update/skip counts match the submitted records, a match to the preflight's stored table plan when present, and fresh D1 target/project conflict checks. Fixed in-transaction assertions preserve create/update and project-scope semantics. Every core write, the `restore_application_commits` row with `destructive_write = 1`, and audit evidence execute in one bounded D1 batch; any statement failure rolls back the sequence and returns `destructiveWrite: false`. Planning rows and attachment bytes remain on their separate gated paths.
- Restore previews include a non-destructive attachment package plan with metadata counts and source-byte totals. Attachment byte commits remain unavailable until the full package verification, object plan, and destination commit-preflight chain is ready.
- Restore attachment-package preflight dry-runs require owner/producer authorization, matching workspace and snapshot workspace IDs, valid backup timestamps, bounded package-plan counts, and source bytes under the package cap before persisting non-destructive package blockers. Verification requires safe package paths, workspace-prefixed object keys, valid SHA-256 values, and exact count/byte matches. Object planning persists destination candidates; commit preflight requires the exact `RESTORE <workspaceId>` confirmation and proves D1/R2 destination absence. The separate byte commit route then requires the same owner/producer session, CSRF token, confirmation, verification, object plan, recent ready preflight, package/manifest/object hashes, target document, and exact object metadata. The browser re-verifies the ZIP entry before upload; the Worker bounds and re-hashes the body, rejects any existing D1/R2 destination, uses a create-only conditional R2 put, records `stored_r2` intent and destructive commit metadata, compensates a metadata failure, and treats only a fully matching prior commit as idempotent.
- Restore planning dry-runs require owner/producer authorization, matching workspace and snapshot workspace IDs, bounded backup planning records, safe optional source paths, valid record/project IDs, and D1 table-specific comparison before returning create/idempotent/update/rejected previews. They write no restored planning rows. When D1 is available, they persist count-level `restore_planning_previews` metadata with table summaries, rejected indexes/reasons, and update field keys, not current/incoming field values.
- Restore planning commits require owner/producer authorization, CSRF/session checks, exact `RESTORE <workspaceId>` confirmation, matching approved approval row, matching blocked commit attempt, matching blocked application preflight row, verified stored R2 pre-restore backup proof, a matching durable `restore_planning_previews` row, at most 150 planning records, and a fresh stale-preview recheck. Duplicate IDs, project-scoped production roles, and invalid timestamps are rejected. Fixed in-transaction assertions preserve approved create/update semantics and require project references in the current workspace. Every non-idempotent planning write, the `restore_planning_commits` row with `destructive_write = 1`, and audit evidence execute in one bounded D1 batch; any statement failure rolls back the sequence and returns `destructiveWrite: false`. Attachment bytes and workspace snapshot rows remain blocked from this planning-specific path.
- Backup dry-runs, restore commit dry-run checks, restore approval dry-runs, restore commit-storage dry-runs, restore application preflight dry-runs, workspace snapshot application commits, planning-row commits, restore planning dry-runs, provider dry-run/readiness checks, Notion import preflights, and operation sync replays record D1 audit events with actor member ids when D1 auth/session storage is available. Provider/import/sync audit metadata is bounded to counts, status/configuration booleans, and policy names; it does not store provider credentials, OAuth values, import filenames, email addresses, document bodies, or operation payloads. The protected Worker audit manifest route supports bounded offset pagination and action-prefix filtering, but returns only event IDs, actions, actor/project IDs, timestamps, and metadata key names/counts; raw metadata values remain out of the manifest response.
- Notion imports start with a Worker-owned metadata preflight that requires declared sizes and accepts at most 2,000 entries, 512 MiB aggregate declared bytes, 1,024-character paths, and 255-character content types. Unsafe or oversized manifests are rejected before browser code reads Markdown/CSV contents locally.
- The local Notion ZIP reader accepts only single-disk, non-ZIP64, unencrypted stored/deflated entries and validates UTF-8 paths, exact central-directory bounds, central/local path, flag, and compression agreement, normalized duplicate paths, entry bounds, declared output size, CRC-32, entry count, aggregate uncompressed bytes, and compression ratio. After Worker preflight, folder and ZIP readers read only returned candidate paths; text reads and ZIP inflation are sequential, and inflation hard-stops at the declared or 25 MiB per-entry limit.
- Notion import application is limited to the previewed candidate plan. CSV parsing is bounded by characters, rows, columns, and cell length; malformed trailing quoted rows and ambiguous headers are ignored with warnings. HTML exports remain unsupported and are not read or imported.
- Screenplay imports are local and private by default. The importer accepts bounded `.fountain` and `.fdx` files after safe-path checks, rejects Final Draft DTD/entity declarations, and deterministically creates revision, scene, element, occurrence, provenance, and review-state records in the IndexedDB workspace. `.gwx` remains metadata-only. Source text and the graph can enter encrypted workspace backups or an explicit user-requested plaintext JSON export, but never operation payloads, Worker requests, D1, provider logs, or model calls.
- Screenplay revision comparison and carry-forward remain local and deterministic. Scene matching uses unique scene numbers, exact normalized content, then same-heading positional matching; no model or provider sees the script. Review-state carry-forward applies only from the selected local base during a one-file import. The explicit planning action creates draft schedule, budget-assumption, and availability copies and relinks only exact matched shot/talent/location identities; unresolved records remain attached to the prior revision. It never rewrites final call sheets, sides, production reports, or prior schedules. The local Markdown revision report is metadata-only and excludes screenplay source text, contacts, provider credentials, OAuth values, raw attachment bytes, raw paths, and private Worker state.
- Screenplay search executes only over the selected in-memory local breakdown and does not persist the query to IndexedDB or localStorage. Manual scene tags store only a bounded normalized element name, category, selected-scene/line reference, bounded excerpt, confirmed review state, and local timestamps in the existing breakdown graph. They share the parser's graph caps and never create operation payloads, Worker requests, D1 rows, provider logs, or model calls. Source text remains unchanged.
- Breakdown scene ordering is a local projection over stable scene IDs in the selected screenplay and matching stripboard. It stores only the `script` or `schedule` UI preference, copies no scene or schedule content, appends missing source scenes instead of hiding them, and creates no Worker request, operation, D1 row, provider request, or model call.
- The screenplay Element List is a transient local projection of active elements and non-dismissed occurrences in the selected revision. It does not copy screenplay source text or occurrence excerpts into report rows. Its local occurrence navigator uses scene IDs, headings, source-line numbers, and review states only. Reusing one existing element or explicitly pasting up to 100 visible active elements delegates to the same bounded local occurrence helper and never changes source text or creates a Worker operation. The in-app copied selection contains only a revision ID, source scene ID, label, and element IDs; it is never written to the OS clipboard, local storage, backup, or Worker and clears on reload or revision change. Batch validation completes before mutation and stale or dismissed IDs fail closed. Duplicate suggestions compare at most 300 active names in the selected category by deterministic normalized text, term overlap, and bounded edit distance; no script text, excerpt, name, or result leaves the browser or enters a model call. Film never auto-merges. An explicit canonical merge combines only the selected local element pair, deduplicates exact scene/line collisions, relinks live availability/location/talent IDs, and leaves issued call-sheet cast snapshots unchanged. Explicit category moves retain the occurrence graph and use that merge path for exact destination collisions. A move fails closed when its destination would invalidate a live availability, location, or talent reference; historical call-sheet cast snapshots are counted and preserved. Category selection, validation, and mutation stay local and create no Worker operation or model call. Explicit Markdown and formula-safe UTF-8 CSV exports contain only element source/review metadata, counts, scene identifiers/headings, first-occurrence metadata, and ordered scene/line positions; they omit screenplay text, contacts, provider credentials, OAuth values, attachments, raw paths, and private Worker state. The separate breakdown JSON remains the only explicit full-plaintext screenplay export.
- Production schedules, bounded scene-part line ranges, main/second-unit identity, availability windows, DOOD rows, explicit Travel/Hold cast-day annotations, scenario assumptions, and schedule-budget scenarios are local and private by default. They reference screenplay graph IDs, enter encrypted workspace backups, and use deterministic schema analysis without a model. Multi-strip selection contains only a schedule ID plus at most 200 scene or scene-part IDs, stays in application memory, and clears after use, structural mutation, version change, or reload. The shared batch helper validates the destination and every deduplicated strip before mutation, then delegates to the existing single-strip transitions; locked schedules return unchanged. Work cannot be manually overridden because it is derived from assigned scenes; annotation writes require an active cast element and existing day, are bounded, deduplicated, disabled on locked schedules, and drop unresolved identities during revision carry-forward. Scene splitting stores source scene ID, `A`/`B` label, and validated start/end lines only; it never duplicates or changes screenplay text. Same-date cross-unit cast use is a blocking local conflict; consecutive-day analysis is calculated per unit. Schedule-budget rates are explicit user-entered integer-cent values, default to zero, and are not sent to the Worker. An explicit stripboard JSON export includes schedule/resource/unit/split/Travel/Hold metadata, analysis, and the optional estimate under `user_requested_schedule_metadata_export`, but omits screenplay and scene source text. Scheduling and estimate state never enter operation payloads, Worker requests, D1, provider logs, or model calls.
- Production shots are local and private by default.
